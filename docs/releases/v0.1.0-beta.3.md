# caixonho v0.1.0-beta.3

A hotfix. **The macOS builds of `v0.1.0-beta.1` and `v0.1.0-beta.2` could not
be opened on any Mac that downloaded them**, and this is the build that can.
Nothing else a user can see has changed since `v0.1.0-beta.2`; its notes remain
the description of what this application does.

## What was wrong

Downloading either earlier macOS asset and opening it produced:

> **"Caixonho" is damaged and can't be opened. You should move it to the Trash.**

with no *Open Anyway* offered anywhere — and the release notes for both
described a different dialog, one with a way through, that nobody opening those
assets could have seen. It stood for nine days. Nobody reported it, and that is
the shape of this failure: "damaged, move it to the Trash" reads as a bad
download, and someone who meets it downloads again and then gives up quietly.

The cause was in how the `.app` was assembled. The linker signs the bare binary
ad-hoc at build time; the bundle was wrapped around it afterwards and was never
signed *as a bundle*, so its only signature predated the bundle itself —
`Info.plist` unbound, no sealed resources. Gatekeeper's own words for that
state, from `codesign --verify --deep --strict` on the released zip, are *"code
has no resources but signature indicates they must be present"*: a bundle
altered after signing, as far as it can tell. That is what "damaged" means.

## What changed

The bundle is now ad-hoc signed as a bundle, which seals `Info.plist` and writes
`_CodeSignature/CodeResources`. The same download now verifies — *valid on disk,
satisfies its Designated Requirement* — and Gatekeeper treats it as an
untrusted-but-intact app: it still refuses the first open, but it now records
the refusal, and that record is what makes **Open Anyway** appear in System
Settings. The earlier assets never got that far — Gatekeeper could not even
identify them — so there was nothing to allow. A verification gate in
the packaging script fails CI if a bundle ever ships unsealed again; on the two
earlier assets that gate is red.

This is still not signing in the sense that matters — no Developer ID, no
notarization. Those are milestone M4, as before.

## What changed underneath, and why it is worth one line

The adapter's real-service test tier (`XONHO-0031`) now also drives six whole
flows from the window's own controls — open a bucket, drop a file, download a
row, tick rows and confirm a delete, delete a folder, preview — against a real
S3 service the tests start, on both CI targets. Nothing about this is visible
in the window. It is why the roadmap can now say, for six of its rows, that a
real service agreed with what the window claims.

## The warning you will see, and what it means

These builds are **not signed by a developer identity and not notarized**.

- **macOS**: the first open is refused. **On current macOS (15 Sequoia and
  26) the dialog says *"Caixonho" is damaged and can't be opened* even for this
  build** — that is Gatekeeper's wording for *untrusted*, not for a broken
  file; the bundle verifies, and the system log for the refusal reads *"Code
  did not match any currently allowed policy"*. Click **Cancel**, not Move to
  Trash. That attempt registers the block. Then open **System Settings →
  Privacy & Security**, scroll to the bottom of the *Security* section to
  *"Caixonho" was blocked to protect your Mac*, and click **Open Anyway**;
  confirm once more. The offer is only there for about an hour after the
  attempt, so do it straight away. Measured on 2026-09-05 on macOS 26.6.2 with
  this exact asset — the earlier notes described this step from documentation,
  and two of them were wrong.
- **Windows**: SmartScreen's *"Windows protected your PC"* → **More info → Run
  anyway**.

Both are doing their job. caixonho reads AWS credentials, so clicking through
them is a decision rather than a formality — do it only for a build you fetched
yourself from this repository's own release page, and not because someone sent
you a file.

## If Open Anyway does not appear, or you would rather not click through

Removing the download's quarantine mark makes Gatekeeper skip the app
entirely. Do this only for a copy you downloaded yourself from this release
page:

```
xattr -d com.apple.quarantine /Applications/Caixonho.app
```

For a copy of an **earlier** build, first give it the sealed signature CI now
applies, then either path above works:

```
codesign --force --sign - /Applications/Caixonho.app
```

## Reporting something

Logs are local and carry no telemetry: `~/Library/Logs/caixonho` on macOS,
`%LOCALAPPDATA%\caixonho\logs` on Windows. They record bucket and connection
names, so read one before attaching it to anything public.
