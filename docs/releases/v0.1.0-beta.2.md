# caixonho v0.1.0-beta.2

The second build offered outside the machine it was written on. One feature
carries it, and it is the one the owner asked for twice while using the
previous build: **acting on a row where the row is, and acting on more than one
of them.**

Everything in `v0.1.0-beta.1` is still here and still true. This describes what
changed; the previous notes remain the fuller picture of what this application
is.

## What is new

**Right-click a row.** The things you can do to an object now live on the
object, in a context menu, rather than as verbs in a toolbar that had outgrown
its row — seven of them beside a breadcrumb that can carry a sixty-character
directory-bucket name. That row had been patched twice: once when `Type a
location` was clipped off the end, once when a bucket's name drew *on top of*
the buttons.

**Tick more than one row, and act on the selection.** Until now nothing but a
single row could be selected, so `Delete…` could only ever mean one object.

**Delete several at once, through a confirmation that says how many.** That
count is the thing the brief asks for and a single-object confirmation never
needed. One object still gets its exact key rather than a count of one, because
a name beats a number when the number is one.

**Delete a folder.** The same act, and the reason it was refused outright
before: it means every object under that prefix. The prefix is walked first
with the delimiter left off — so the count is the whole subtree, not its top
level — and that count is what the confirmation states before anything is sent.
Deleting `daily/` when its grouped listing shows two rows and three objects
live under it now says three.

**Destructive actions are in the context menu only, never on hover.** A delete
icon under the cursor is easier to hit by accident than a double-click, and
double-click is already deliberately unbound so that a stray one cannot write
company bytes to disk. The confirmation would catch a misclick; that is not a
reason to lay a trap.

**The toolbar keeps only what acts on a place** — upload, new folder, and the
path.

Deletes run through the queue `v0.1.0-beta.1` shipped: bounded concurrency, and
a refusal keeps its own key and its own cause instead of failing the batch.

## What is not in it

The previous notes' list stands, and these are the parts of it this release
touches or adds to.

- **No Undo after a bulk delete.** Undo is offered when the service's own
  response proves a delete marker exists. For many objects that is many
  markers, and a partial restore is its own design — so a bulk delete says
  plainly that it is not offered rather than offering something it cannot
  finish.
- **A prefix holding more than 5,000 objects is refused with a reason rather
  than walked.** Whether that walk should be streamed and cancellable is a
  question this release answers only as far as the count it shows.
- **No copy, move or rename**, so there is no way to move things out of a
  prefix that is over the ceiling before deleting it.
- Still no installer, no signing, no pause or resume, no throughput or ETA, no
  multipart — files above 5 GiB are still refused up front — no folder upload,
  no sorting, and no server-side prefix search.
- **Signing in to IAM Identity Center from the app is still unproven.** Treat
  the AWS CLI as required for SSO.
- **macOS builds are Apple Silicon only.**

## What changed underneath, and why it is worth one line

The adapter that turns this project's intentions into HTTP now has a test tier
that sends real requests to a real S3 service the tests start themselves. Two
tiers already existed and neither sent a request: one answered above the
adapter, one replayed bytes below it. Between them sat the question neither
asked — does the request we build mean, to a real service, what we believe it
means?

Nothing about this is visible in the window. It is here because the listing,
pagination, conditional-write and delete behaviour this release leans on are
what it exercises.

## The warning you will see, and what it means

These builds are **not signed and not notarized**.

- **macOS**: *"Apple could not verify caixonho-gui is free of malware."* That
  means unverified, not malicious. **System Settings → Privacy & Security →
  Open Anyway.**
- **Windows**: SmartScreen's *"Windows protected your PC"* → **More info → Run
  anyway**.

Both are doing their job. caixonho reads AWS credentials, so clicking through
them is a decision rather than a formality — do it only for a build you fetched
yourself from this repository's own CI, and not because someone sent you a file.

Signed and notarized builds are milestone M4.

## Reporting something

Logs are local and carry no telemetry: `~/Library/Logs/caixonho` on macOS,
`%LOCALAPPDATA%\caixonho\logs` on Windows. They record bucket and connection
names, so read one before attaching it to anything public.
